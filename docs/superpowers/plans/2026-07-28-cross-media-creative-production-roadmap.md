# Creative Claw 跨媒介创作工业化系统实施路线图

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将 Creative Claw 从单画布叙事工具升级为支持长篇小说与竖屏短剧的、可配置、可审阅、可追踪的跨媒介创作生产系统。

**Architecture:** 保留现有本地优先 Flask + SQLite 架构，以“生产工作流内核”为领域中枢，把来源、实体、关系、时间线、正文、K 线、版本、审阅、影响记录和 AI 提案统一挂接到项目、阶段、生产单元与交付物。前端按写作、结构、审阅三种主模式渐进改造，先修复真实上下文联动，再加入工作流、引导和影响中心，避免一次性重写现有系统。

**Tech Stack:** Python 3、Flask、SQLite、原生 HTML/CSS/JavaScript、Python `unittest`、Node.js 内置测试运行器、Playwright、OpenAI-compatible Chat Completions API。

## Global Constraints

- 首版媒介只内置“长篇小说”和“竖屏短剧”，架构允许后续扩展电影、长剧、漫画、游戏和音频剧。
- 面向单人创作者；AI 是纯副驾驶，只在用户明确发起任务后工作，不自动推进工序。
- AI 只生成分析、候选稿、提案、补丁和审阅问题，不直接覆盖正式稿。
- 工作流采用“标准模板 + 可配置阶段”，允许增删、重排和重命名阶段。
- 前端只面向桌面浏览器；首版不做手机端。
- 正文编辑器必须脱离缩放画布。
- 上游修改必须产生影响记录，并将相关下游审阅标记为过期。
- K 线修改不自动改正文，但必须更新父周期、AI 上下文、影响记录、连续性检查、审阅状态和账本。
- 所有正式稿修改必须生成新版本；拒绝 AI 提案后正式稿保持不变。
- 账本保持不可变并可校验；迁移后旧项目仍可打开、搜索、编辑和验证。
- 自动测试默认不得消耗真实模型费用；仅 `CREATIVE_CLAW_REAL_LLM_TEST=1` 时执行真实模型测试，密钥不得进入源码、数据库、浏览器存储、报告或日志。
- 项目当前不是 Git 仓库；只有 `git rev-parse --is-inside-work-tree` 成功时才执行计划中的提交命令，否则只记录变更文件和建议提交信息，不得自动初始化 Git。

## 阶段依赖图

```text
Phase 1 上下文与联动修复
        ↓
Phase 2 生产工作流内核
        ↓
Phase 2.5 参考机制蓝图迁移与安全草稿
        ↓
Phase 3 写作 / 结构 / 审阅三模式
        ↓
Phase 4 首次向导 + 持续工序助手 + 媒介模板
        ↓
Phase 5 影响中心 + 锁稿/导出 + 工业化验收
```

每个阶段都必须产出可单独运行、可回归、可浏览器验收的软件，不以“页面已出现控件”作为完成标准。

## Phase 1：修复现有上下文与真实联动

**目标：** 消除演示人物硬编码，让当前项目、分支、章/集、场景、人物和维度真正贯穿浏览器、API、检索器、模型上下文、证据展示与测试。

**核心交付：**

- `ContextScope` 统一上下文契约与旧请求兼容解析。
- 当前场景、相邻时间线和关联场景 K 线自动进入上下文。
- 来源、图谱、时间线、K 线、版本、规则、问题使用独立证据编号。
- 调模型前提供“模型上下文预览”，用户能看到 AI 将使用什么。
- 浏览器不再出现写死的“沈霜 / 知情度”。
- API 返回 `resolved_scope`、`evidence_refs` 和 `citation_validation`。
- 浏览器 E2E 证明切换场景或人物后，请求、预览和回答证据同步变化。

**详细计划：** `docs/superpowers/plans/2026-07-28-phase1-context-linkage.md`

**退出条件：** 原有测试不回归；新增 Python、Node 和浏览器测试通过；真实模型测试在显式启用时能证明时间线和 K 线已进入模型上下文。

## Phase 2：生产工作流内核

**目标：** 建立媒介无关的项目生产模型，使“阶段—生产单元—交付物—版本—依赖—审阅—影响”成为后端的一等对象。

**建议领域对象：**

- `workflow_template`：标准模板定义与版本。
- `workflow_stage`：阶段顺序、名称、说明、进入条件、完成标准。
- `production_unit`：卷/章、季/集/场等层级单元。
- `artifact`：故事圣经、人物小传、大纲、正文、分集梗概、剧本等交付物。
- `artifact_version`：不可覆盖的内容版本和状态。
- `dependency_edge`：上游与下游的显式依赖。
- `review_record`：审阅结论、依据版本、有效或过期状态。
- `impact_record`：变更源、传播路径、风险、处理状态。

**实施边界：**

- 先新增迁移和领域服务，不删除现有 `documents`、`timeline_events`、`ohlc_points`、`ledger_events`。
- 旧 `document` 映射为来源类 `artifact`，旧场景正文映射为正文类 `artifact`。
- 阶段状态变更必须经过服务层规则校验，不允许前端直接写数据库状态。
- 无模型配置时，用户仍可手工完成全部阶段和审阅。

**退出条件：** 长篇小说和竖屏短剧模板都可实例化；生产单元与交付物可创建版本；依赖修改会使对应审阅过期；迁移测试证明旧项目数据完整。

## Phase 2.5：参考机制蓝图迁移与安全草稿

**目标：** 从作者提供的成品参考文本抽取全部可观察创作机制，并把抽象机制迁移到不同人物、世界和冲突中；作者确认目标生产蓝图后才按单元生成草稿。

**已完成交付：**

- 受确定性 DAG 编排的多代理抽取、长篇持久化分批和暂停/恢复/取消；
- 全部维度三态、绝对证据范围、置信度、多解释、冲突和不可覆盖蓝图版本；
- 自然语言新设定结构化、机制 preserve/transform/drop/add 映射与目标生产蓝图确认门禁；
- 草稿上下文 allowlist 和 reference provenance 防火墙；
- 表达复制、独特结构与抽象机制三层相似度门禁；
- candidate 接受/拒绝、并发版本冲突、账本与影响传播；
- 桌面“蓝图实验室”、HTTP API、短文本和长篇后台浏览器 E2E。

**详细计划：** `docs/superpowers/plans/2026-07-29-phase2.5-reference-blueprint-migration.md`

**退出条件：** 短/长两条路径可运行；草稿请求不含参考正文；复制候选不能接受；通过候选接受后创建正式版本；旧 Phase 1/2 行为无回归。

## Phase 3：写作 / 结构 / 审阅三模式

**目标：** 重组桌面端信息架构，让用户在任一时刻只面对一个主任务，同时保留跨模式共享选择状态。

**写作模式：**

- 独立正文编辑器，不受结构画布缩放和平移影响。
- 左侧显示生产单元导航；中间写作；右侧显示当前工序、AI 提案和上下文摘要。
- 保存正式稿生成新版本，不原地覆盖。

**结构模式：**

- 承载实体关系、时间线、场景、生产单元结构和 K 线关联。
- 画布缩放只影响结构视图。
- 选择场景后同步更新全局 `ContextScope`。

**审阅模式：**

- 集中展示版本差异、连续性问题、K 线、账本、审阅记录和待处理影响。
- 可接受、拒绝或撤销 AI 提案；接受生成新版本与影响记录。

**退出条件：** 三模式切换不丢当前项目、单元、场景、人物和维度；正文编辑不随画布缩放；桌面端常用操作无需打开全部面板。

## Phase 4：首次向导、持续工序助手与媒介模板

**目标：** 新用户不读 README 也能创建项目、理解当前工序、完成必要输入并知道下一步。

**首次建项向导：**

1. 选择媒介模板：长篇小说或竖屏短剧。
2. 填写项目名称、核心概念、目标受众与计划规模。
3. 确认标准阶段，可增删、重排、重命名。
4. 创建首批生产单元和必需交付物。
5. 进入首个未完成工序。

**持续工序助手：**

- 固定显示当前项目、当前生产单元、当前阶段和完成度。
- 解释该工序为何存在、需要哪些输入、将产出什么、完成标准是什么。
- 明确列出缺失项、阻塞原因、建议下一步和影响提醒。
- 提供精简、标准、详细三种引导密度，不替用户自动推进。

**退出条件：** 两种模板都能从向导走到首个可写作工序；阶段配置可保存；刷新后仍能恢复当前工序；无模型也能完成向导。

## Phase 5：影响中心与工业化验收

**目标：** 把每次上游修改变成可追踪、可审阅、可关闭的影响工作项，并完成长篇小说与竖屏短剧端到端验收。

**影响中心：**

- 显示变更来源、源版本、受影响资产、传播路径、风险级别和处理状态。
- 区分“系统确定影响”和“需要作者判断的潜在影响”。
- K 线变化触发父周期重算、关联场景连续性检查、审阅过期和上下文刷新，不改写正文。
- 正典、人物事实、时间线、故事圣经或正文上游版本变化时，计算下游依赖并生成影响记录。

**锁稿与导出：**

- 锁稿前检查必需交付物、有效审阅、未关闭高风险影响、版本冲突和账本校验。
- 锁稿产生明确版本；例外必须记录理由和操作者。
- 导出只读取已锁定版本，首版不自动发布或备案。

**端到端验收项目：**

- 长篇小说：向导 → 故事圣经 → 人物/结构 → 章节写作 → 审阅 → 影响处理 → 锁稿 → 导出。
- 竖屏短剧：向导 → 项目资料 → 分集/场景 → 剧本写作 → 合规与连续性审阅 → 影响处理 → 锁稿 → 导出。
- 两个项目都验证 AI 接受、AI 拒绝、上游修改、K 线修改、审阅过期、账本校验和无模型路径。

**退出条件：** 规格第 23 节功能、联动、AI 和用户体验验收项全部有自动化证据；关键失败能定位到具体生产对象、版本和影响记录。

## 跨阶段质量门

每个阶段结束前统一执行：

```powershell
.\.venv\Scripts\python.exe -m compileall creative_claw tests
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
node --check creative_claw/web/app.js
```

存在 `tests/js` 时追加：

```powershell
node --test tests/js/*.test.cjs
```

存在对应 Playwright 脚本时，以隔离数据库和独立端口运行浏览器验收。真实模型验证仅在调用者显式注入临时环境变量时运行，测试结束后清除进程环境变量并确认报告中没有密钥。

## 计划维护规则

- 每个后续阶段开始前，基于上一阶段已落地接口再写独立详细计划，避免提前锁死未实现细节。
- 若阶段实施改变了公共接口，先更新设计规格和路线图，再更新后续计划中的接口名。
- 阶段交付记录必须列出修改文件、测试命令、测试结果、已知限制和建议提交信息。
- 不得以截图替代 API、数据库、账本和浏览器行为验证。
